# CNC Tool Database Professionalization Plan

This project is moving from an experimental tool viewer into a trustworthy CNC tooling knowledge base. The cleanup goal is not only prettier code; it is a database that can explain why a tool, spec, or compatibility claim is trusted.

## Target Standard

- One canonical database is used by scripts, UI, and publishing.
- Every catalog fact can be traced to source evidence.
- Compatibility is represented as edges with verification status, not loose prose.
- Shop-proven fit is kept separate from catalog or inferred compatibility.
- Audit scripts are read-only by default and safe to run before any cleanup.
- Data updates are reviewed before apply.

## Canonical Data Direction

`docs/db_v2.sqlite` is the preferred long-term shape because it separates:

- `catalog_tools`: tool identity and shared catalog fields.
- `sources`: manufacturer pages, catalogs, manuals, shop notes, and local files.
- `tool_specs`: source-backed technical facts.
- `compatibility_edges`: mounts-to, accepts-insert, and machine compatibility claims.

`docs/db.sqlite` is still the current published UI database. It should be treated as the legacy publishing source until the UI is migrated to v2.

## Verification Levels

Use these meanings consistently in data, scripts, and UI:

- `unverified`: present in the database but not backed by usable evidence.
- `imported`: carried from older data; useful but not yet rechecked.
- `catalog_claim`: backed by a manufacturer catalog or local catalog file.
- `manufacturer_verified`: backed by a manufacturer-hosted product page or current manufacturer source.
- `shop_verified`: physically confirmed in the shop or on the actual machine.
- `inferred`: generated by a rule, such as ISO seat matching; never equivalent to verified fit.
- `rejected`: retained for audit history but known wrong.

## Cleanup Phases

### Phase 1: Stabilize the Workbench

- Add reliable read-only audit commands.
- Identify which database is canonical for each workflow.
- Remove stale assumptions from docs and scripts.
- Keep database rows unchanged.

### Phase 2: Normalize Provenance

- Convert free-text source strings into structured source records.
- Link tools, specs, and compatibility edges to source records.
- Record catalog file, page, URL, source type, and evidence notes.
- Flag text-only sources that need exact catalog/page confirmation.

### Phase 3: Tighten Compatibility

- Use compatibility edges as the primary relationship model.
- Keep `mounts_to`, `accepts_insert`, and `compatible_with_machine` separate.
- Treat ISO/seat matches as inferred until checked against catalog or shop fit.
- Model bushings/adapters as first-class compatibility nodes when they bridge holder shank size/shape to station size/shape.
- Distinguish round shank, square shank, modular receiver, and machine-station interface types.
- Require shop verification for actual machine-station fit.

### Phase 4: Move the UI to v2

- Load `catalog_tools`, `tool_specs`, `sources`, and `compatibility_edges`.
- Show verification badges per fact and per relationship.
- Make sources visible and clickable where possible.
- Add filters for verified, catalog claim, inferred, and unverified records.
- Clean up tables, filters, and detail views so the data is easier to scan and compare.
- Add compatibility-tree filtering for insert -> holder/module -> adapter/bushing -> machine station paths.
- Add physical-interface filters such as round shank, square shank, shank size, station type, and adapter needed.

### Phase 5: Expand Catalog Coverage

- Review the catalog folder for additional manufacturer catalogs that apply to the machines.
- Add tools through a repeatable proposal/import workflow, not direct database edits.
- Prioritize tools that can fit existing machines, stations, holders, adapters, or modular shank systems.
- Preserve source evidence for every imported tool and compatibility claim.
- Keep catalog import scripts manufacturer-specific when table formats differ.

### Phase 6: Repository Hygiene

- Move backups, logs, generated previews, and unrelated assets out of the published app path.
- Keep only one published database file.
- Document the publish command and database build path.
- Add a small regression checklist for data audits and UI smoke tests.

## First Cleanup Targets

- Add shop-note evidence and explicit from/to size and shape fields for the three generic bushing adapter rows.
- Normalize `Horn` vs `PH Horn` manufacturer naming.
- Review unresolved compatibility notes.
- Decide whether `docs/db_v2.sqlite` should replace `docs/db.sqlite` as the UI source.
- Replace or retire stale root-level audit scripts that no longer match the current database.
